  https://docs.expo.dev/versions/v54.0.0/ 의 버전별 문서를 확인할 것.
- **검증 워크플로우**: 뭘 고치든 항상 `npx tsc --noEmit -p .` → `npx eslint . --ext .ts,.tsx` 순서로
  돌려서 확인함 (저장소 루트 `d:\cowork\moa-app`에서 실행). 항상 클린해야 정상이고, 유일하게
  예외인 건 `.expo/types/router.d.ts`의 "Unused eslint-disable directive" 경고 하나뿐(무해한

## 기능별 현재 상태 & 이유

### 1. 홈 화면 = "내가 찜한 것만" 캘린더 (가장 큰 구조 변경)

전에는 "찜한 정책" 전용 탭이 따로 있었는데, 사용자가 명시적으로 확인(AskUserQuestion) 후 **그
탭을 없애고** 홈 화면 자체를 "찜한 것만" 보여주는 캘린더/목록으로 바꿈. 관심분야 칩(전체+5개
카테고리)은 그대로 유지, 거기에 `savedIds.has(d.id)` 필터가 추가로 걸림. 탭바는 **홈 + 전체
2개**로 줄어듦.

- 캘린더 점(dot)은 항상 "신청 시작일" 기준(마감일 기준으로 찍으면 마감일까지 매일 뭔가 있는 것처럼
  보여서 헷갈림). 우측 하단에 안내문구: "캘린더는 '찜'한 공고 신청 시작일을 표시합니다".
- 목록은 진행 중 / 예정 / 마감 3개 섹션으로 분리 (`lib/deadlineUtils.ts`의 `computeDday` phase 기준).
  전엔 마감 섹션이 0건이면 안 보였는데, 찜 기반으로 바뀌면서 그게 이상해 보여서 **항상 렌더링**하고
  0건이면 빈 문구만 보여주는 걸로 수정함.
- 정렬 토글(`renderSortToggle()`) — **오늘(08-22~23) 검색 화면과 통일함**: 인기순/지원 가능순이
  서로 독립적인 체크박스(둘 다 켤 수 있음, 배타적 아님). 둘 다 꺼지면 기본값(마감순) — 진행중/예정은
  마감일 빠른 순 오름차순, 마감 섹션은 최근에 마감된 것부터(내림차순). 이 토글은 진행중/예정/마감
  섹션 + 날짜 선택했을 때의 목록까지 전부 동일 로직 공유 (`sortHomeList()` 헬퍼).
  - **주의**: 예전엔 "인기순 vs 지원가능순"이 서로 배타적(하나 누르면 다른 게 꺼짐)이었는데
    2026-08-23에 검색 화면과 똑같이 "동시에 켤 수 있게" 바꿔달라는 요청으로 변경됨. `HomeSortMode`
    타입(`'none'|'popular'|'eligible'`)을 없애고 `homeSortPopular`/`homeSortEligible` 두 개의
    독립 boolean으로 교체함.
- 검색창(진짜 검색 아님, `/search`로 이동하는 트리거): 문구는 여러 번 다듬어져서 최종
  "나와 'Fit'한 공고 '찜'하기!" (위에 힌트 줄 "모든 공고가 보고싶다면?").
- 상단 바: 🔔(알림, `/notifications`)와 👤(프로필, `/edit-profile`) 아이콘. 색은 연한 초록
  `#9FDAC0`, 원형 배경 없음(아이콘만).

### 2. 검색 화면 (`app/search.tsx`)

- 카테고리 줄: 전체(하늘색 `#4FC3EE`) + 5개 카테고리. 마지막 카테고리 하나까지 끄면 자동으로
  "전체"로 되돌아감(0개 선택 상태 자체를 없앰 — 예전에 그 상태에서 검색결과 0건 + 레이아웃 버그가
  있었음).
- 정렬/필터 토글 — **2026-08-23 기준 순서와 의미가 바뀜**:
  **인기순 → 지원 가능순 → 찜만 보기 → 마감된 공고 제외**
  - "찜 우선"(정렬 가중치)이었던 걸 **"찜만 보기"(순수 필터)**로 바꿈. `savedOnly`가 켜지면
    `excludeClosed`처럼 그냥 목록에서 안 찜한 건 다 빠짐 — 정렬엔 관여 안 함.
  - 인기순/지원가능순은 여전히 서로 독립(체크박스), 둘 다 켜면 인기순이 먼저 적용되고 동점일 때만
    지원가능순으로 다시 나뉨.
  - 아무 정렬 토글도 안 켜져 있을 때 기본 정렬: 마감 안 된 건 위, 마감된 건 아래로 가라앉고,
    그 안에서 마감 안 된 건 마감일 빠른 순, 마감된 건 최근 마감 순.
  - **정렬 우선순위 관련 중요 규칙**(사용자가 명시적으로 두 번 정정함): 인기순/지원가능순 같은
    "사용자가 직접 켠 정렬"은 마감 여부보다 우선함 — 즉 마감된 공고라도 인기가 많으면 그 기준으로
    위로 올라올 수 있음. 마감된 걸 아예 안 보고 싶으면 "마감된 공고 제외"를 따로 켜야 함.
- 각 토글 줄(카테고리 줄, 정렬 줄)은 가로 스크롤인데, 예전에 "검색어를 입력해서 결과가 0건이 되면
  줄 높이가 갑자기 커졌다가 지우면 원래대로 돌아오는" 버그가 있었음. 여러 번 시도 끝에(아래
  "해결한 버그" 참고) **ScrollView를 높이 고정+overflow:hidden인 일반 View로 감싸는** 패턴으로
  확정.

### 4. 찜 개수(인기도) 기능

- `saved_policies` 테이블은 RLS로 자기 행만 조회 가능해서, 전체 찜 개수 집계를 위해 별도
  Supabase **VIEW**를 만듦: `supabase/policy_save_counts.sql` (policy_id, count만 노출, user_id
  없음, `authenticated`에 GRANT SELECT). **이 SQL, 아직 Supabase SQL Editor에서 수동 실행
  안 했으면 인기순 관련 기능이 전부 0으로 보임 — 외부 작업 필요, 잊지 말 것.**
  - `lib/usePolicySaveCounts.ts`가 이 뷰를 읽어서 `Map<policyId, count>` 제공.
  - `components/deadline-card.tsx`가 하트 버튼 아래 작은 숫자로 찜 개수 표시(0이면 숨김).
  - 찜 버튼 누른 직후 카운트가 바로 안 늘어나 보이는 버그가 있었음 → `onToggleSave`에서
    `await toggleSaved(...)` 직후 `refreshSaveCounts()` 즉시 호출해서 해결.

### 8. "전체" 탭 (`app/(tabs)/more.tsx`)

사용자가 준 스펙 그대로: MY(내 정보→실제 연결, 내가 지원한 공고→준비 중) / 커뮤니티(내가 쓴
글·댓글→둘 다 준비 중) / 회원(로그아웃→실제 동작, 회원탈퇴→**부분 구현**: `saved_policies`+
`profiles` 행은 지움+로그아웃까지 하지만 **실제 Supabase Auth 계정 자체는 안 지워짐** — 그건
서버 사이드 Edge Function(admin API)이 있어야 가능해서 클라이언트 코드로는 못 함, 명시적으로
코드 주석에 남겨둠) / 서비스(개인정보 처리방침 → `/privacy-policy` 연결).

### 9. Fit Me 로고 (`components/fit-me-logo.tsx`)

여러 번 완전히 갈아엎음: 카메라 뷰파인더 프레임(민트 코너 브래킷) → 손 모양 SVG(반려, 참고 이미지랑
너무 달라짐) → 다시 추상적인 민트 프레임 + 기울어진 "F" → "Fit Me 기울지말아줘" 요청으로 기울기

       세 지역은 전부 틀리게 잡혔을 것). 재동기화 결과 regionKeyword 보유율이 365/517(71%) →
       **490/517(95%)**로 크게 늘었고, 아산/홍성 정책들은 이제 "충청남도"로 정확히 잡힘(zipCd만으론
       시/군 단위까진 못 잡고 도 단위까지만 — 정확한 법정동 코드표가 없어서 그렇지만, 지역
       제한을 아예 놓치는 것보단 훨씬 나음).
    2. **"전남광주통합특별시"가 옛 지역명(광주광역시)으로 잘못 잡히던 문제** — 처음엔 이 이름을
       그냥 "두 지역이 합쳐진 것처럼 보이는 이름" 정도로만 취급하고 넘어갔었는데, 실제로 확인해보니
       광주광역시+전라남도가 진짜로 통합된 현재(2026년 기준) 정식 광역자치단체명이었음(위키백과로
       확인). 관련 정책 86건이 전부 org_name에 이 이름을 정확히 쓰고 있었는데, 기존 코드는 약칭
       매칭 순서상 먼저 걸리는 "광주" 약칭에 매번 걸려서 옛 "광주광역시"로 잘못 저장되고 있었음.
       "전남광주통합" 항목을 최우선으로 검사하도록 고치고, [constants/regions.ts](../../../constants/regions.ts)의

       **후속 조치까지 완료(같은 날)**: 회원가입/프로필 화면의 거주지 선택

       옛 "광주광역시"(자치구 5개)/"전라남도"(시/군 22개) 두 항목을 빼고 "전남광주통합특별시"

       `kind: 'province'`로 두고 구 5개+시/군 22개를 `cities` 배열 하나에 합쳐 넣음(라벨이 구엔
       살짝 안 맞지만 "거주지 (시/군)" 단계에서 둘 다 고를 수 있어 기능은 정확함). 기존에 옛
       지역명을 저장해둔 프로필이 있는지 확인했는데 0건이라 마이그레이션은 필요 없었음.
    3. **판정 가능한 조건이 하나도 없는 정책이 전부 "조건 미충족"으로 잘못 뜨던 문제** —
       `calculateMatch()`가 `criteria.length === 0`일 때 `eligible: false`를 반환하고 있었음(연령/
       소득/무주택/지역 중 어느 것도 데이터에서 못 찾았을 때). 조건을 하나도 못 찾았다는 건
       "막는 조건이 없다"는 뜻이라 반대로 지원 가능이 맞음 — `eligible: true`로 뒤집음. 517건 중
       27건이 여기 해당(주로 소득 조건은 아예 안 다루고, 연령/지역도 다 없는 경우).
    4. **지역 조건이 없는 공고를 카드/상세 화면에서 명시적으로 "📍 전국"이라고 보여주게 추가함**
       — 원래는 regionKeyword가 없으면 아무 표시도 안 해서 "지역 정보를 못 찾은 건지 진짜 전국
       대상인지" 구분이 안 됐음(사용자 피드백). 이제 값이 있든 없든 항상 "📍 {지역}" 또는
       "📍 전국"이 보임([components/deadline-card.tsx](../../../components/deadline-card.tsx),
       [app/deadline/[id].tsx](../../../app/deadline/%5Bid%5D.tsx)).
  - **대학생/취업상태 조건이 프로필에 필드는 있는데 판정에 전혀 안 쓰이던 문제 수정(2026-08-23)**
    — 사용자가 "마이페이지에 대학생 여부/취업준비생 여부 넣어놨는데 대학생 대상 공고가 나한테
    지원 가능이라고 뜬다"고 지적함. 확인해보니 `Requirements` 타입 자체에 연령/소득/무주택/지역
    4개밖에 없어서 프로필 필드는 있어도 매칭 로직이 아예 안 봄. 온통청년 오픈API 공식
    코드정의서(`API코드정보.xlsx`, 페이지에서 직접 다운받아 실측)를 확인해서 `schoolCd`(학력요건
    코드)/`jobCd`(취업요건코드)/`sbizCd`(특화요건코드)의 실제 코드값을 확보함 — 예: schoolCd
    0049005="대학 재학", jobCd 0013003="미취업자", sbizCd 0014003="기초생활수급자"/0014004=
    "한부모가정". `Requirements`에 `requiresUniversityStudent`/`requiresJobSeeker`/
    `requiresBasicLivelihoodRecipient`/`requiresSingleParentFamily` 4개를 추가하고
    `calculateMatch()`(profile의 `is_university_student`/`is_job_seeker`/
    `is_basic_livelihood_recipient`/`is_supported_single_parent_family`와 비교)에 반영함.
    schoolCd/jobCd는 "이 코드 하나만 단독으로 걸린 경우"만 확실한 신호로 보고 반영함(여러 값이
    섞여 있으면 우리 프로필로 정확히 표현 못 하니 조건 없음으로 안전하게 둠). 소득 조건
    (`earnCndSeCd`/`earnMinAmt`/`earnMaxAmt`)은 실측해보니 단위가 정책마다 제각각(어떤 건
    "5000"=5000만원, 어떤 건 "43056240"=원 단위로 보임)이라 잘못 해석해서 틀린 조건으로
    거르느니 이번에도 계속 스킵함(9건뿐이라 영향도 작음). 재동기화 결과 대학생 대상 26건/
    미취업자 대상 68건/기초생활수급자 대상 2건/한부모가정 대상 1건이 새로 판정에 반영됨.
  - **지역 인식 3단계로 보강 + "울산 동구 청년의 날" 같은 사례 수정(2026-08-23)** —
    사용자가 이 공고가 "전국"으로 뜨는 게 이상하다고 지적. 원인은 org_name이 "경제정책국"(부서명뿐)
    이고, **원본 데이터의 zipCd 자체가 전국 코드 목록으로 잘못 채워져 있어서**(산림청/고용노동부
    같은 진짜 전국 대상 정책과 똑같은 패턴 — 온통청년 쪽 데이터 품질 문제로 보임) 우리 zipCd
    보강 로직도 못 잡았음. org_name/zipCd 둘 다 실패했을 때 최후 수단으로 **제목 맨 앞 1~2단어가
    시/도 이름으로 시작하는지**(예: "울산 동구 청년의 날...") 확인하는 3단계를 추가함 — 제목
    중간에 나오는 지역 언급까지 다 스캔하면 오판 위험이 커서 맨 앞만 봄. 이 과정에서
    "OO구" 시/군/구 판별 정규식(`CITY_UNIT_RE`)이 2글자 이상만 인정하고 있어서 "동구"/"중구"/
    "남구"/"북구"/"서구"처럼 1글자+구인 흔한 자치구 이름(부산/대구/인천/광주/대전/울산 전부
    "동구"가 있음)을 놓치고 있던 것도 같이 발견해서 1글자까지 허용하게 고침(오탐 스팟체크
    결과 실제 자치구 이름만 걸림, "특구"/"연구" 같은 오탐 없음 확인). regionKeyword 보유율
    490/517 → **491/517**.
  - **제목 스캔을 맨 앞 1~2단어 → 제목 전체로 확대(2026-08-23, 사용자 요청)** — 지역명이 제목
    중간에 나오는 경우까지 잡으려고 넓힘. 시/군/구 단위(예: "아산", "홍성")까지 전체 스캔하면
    흔한 단어와 겹칠 위험이 커서(예: "영양"=nutrition도 실제 군 이름) 그건 여전히 안 하고,
    상대적으로 안전한 17개 시/도 이름만 전체 스캔 대상으로 함. org명/zipCd 둘 다 실패했을 때만
    쓰는 마지막 수단이라 실질적 영향은 적었음(재동기화해도 regionKeyword 보유율 491/517로 그대로
    — 대부분 이미 앞부분에서 잡히고 있었다는 뜻).
  - **소득 조건(연소득) 추가(2026-08-23, 사용자 요청)** — 처음엔 "정책마다 금액 단위가 달라
    보여서 위험하다"는 이유로 스킵했었는데, 사용자가 그래도 넣어달라고 해서 원문 설명
    (`addAplyQlfcCndCn`/`plcySprtCn`)과 대조해서 실제 9건을 전수 확인함 — earnMaxAmt가
    거의 다 "만원" 단위 그대로였고(5000→5,000만원 등), 딱 1건("청년부부 주거환경 개선사업")만
    "43056240"처럼 원(KRW) 단위였음(만원으로 읽으면 430억원이 돼서 말이 안 되고, 10000으로
    나누면 4,306만원으로 현실적인 값이 됨). 그래서 **100만 이상이면 원 단위로 보고 10000으로
    나눠서 만원으로 통일**하는 규칙을 만듦. 개인 소득인지 가구(부부합산) 소득인지는 설명 텍스트에
    "부부합산" 같은 표현이 있는지로 구분(9건 중 "청년 신혼부부 월세지원" 계열 2건만 부부합산,

    `maxHouseholdAnnualIncome`(연소득, 만원)을 추가하고, `calculateMatch()`에서 프로필의
    월소득×12와 비교함. earnMinAmt(하한)는 우리 시스템에 "하한" 개념이 없어서(9건 중 1건만
    0이 아니었고, 그마저도 청년/청년외/신혼부부별 구간 차이였음) 반영 안 함. 재동기화 결과
    9건 모두 정확히 잡힘(개인 7건/가구 2건).

- **화면당 개별 fetch**: `useProfile`/`useSavedPolicies` 등 기존 훅들과 같은 패턴을 따라서

### 13. 정책 상세 화면 개편 + 댓글 기능 (2026-08-23, 완료 — SQL 실행 필요)

사용자가 경쟁 앱 스크린샷을 보여주며 상세 화면 정보 구성을 요청함. `app/deadline/[id].tsx`를

## 지금까지 근본 원인까지 찾아서 고친 버그들

1. **다크모드에서 탭 아이콘이 안 보임** — `constants/theme.ts`의 `Colors[colorScheme].tint`가
   시스템 다크모드일 때 흰색(`#fff`)을 반환하는데, 이 앱 화면은 라이트 팔레트로 고정돼있어서
   (`app/_layout.tsx` 참고) 밝은 탭바 위에 흰 아이콘이 사라져 보였음. → `app/(tabs)/_layout.tsx`에서
   시스템 설정과 무관하게 `COLORS.mint`/`COLORS.inkSoft`로 하드코딩해서 해결.
2. **검색 화면 토글 줄 높이가 검색 중에 갑자기 커짐** — 4번의 시도 끝에 해결. ScrollView 자체의
   `style={{height}}`만으로는 내부 콘텐츠 크기에 따라 프레임이 재측정되면서 부풀어 오르는 경우가
   있었음. 최종 해결책: ScrollView를 감싸는 바깥 `<View style={{height:N, overflow:'hidden'}}>`을
   추가 — ScrollView 자체 height 스타일에 의존하지 않고 바깥 View가 확실히 못 벗어나게 막음.
3. **홈 화면 "마감" 섹션이 사라져 보임** — `{closedDeadlines.length > 0 && (...)}` 조건부 렌더링이
   원인. 찜 기반으로 바뀌면서 마감 0건인 경우가 흔해져서 다른 두 섹션(진행중/예정)과 다르게
   갑자기 사라진 것처럼 보였음 → 항상 렌더링하고 0건이면 빈 문구로 대체.
4. **검색 카테고리 0개 선택 상태의 데드엔드+레이아웃 버그** — 마지막 카테고리를 꺼서 0개가 되면
   자동으로 "전체"로 되돌리게 수정.
5. **찜 개수가 바로 안 갱신됨** — 찜 토글 직후 `refreshSaveCounts()` 즉시 호출로 해결.
6. **검색 화면 진입이 눈에 띄게 느림(2026-08-23, 실제 데이터 연동 직후 발견)** — 처음엔
   `usePolicies()`의 백그라운드 재조회가 `useSavedPolicies`까지 연쇄적으로 재요청을 일으키는
   문제로 추정하고 그것부터 고쳤는데(캐시 30초 스로틀 + useSavedPolicies 의존성 분리), 사용자가
   "그래도 여전히 또렷이 느껴진다"고 확인해줘서 다른 화면(전체 탭/알림/프로필)은 안 느리고
   검색만 유난히 느리다는 걸 다시 물어봐서 좁힘 — **진짜 원인은 검색어가 비어있을 때 기본으로
   보여주는 전체 목록(500건 넘음)을 일반 `ScrollView` + `.map()`으로 한꺼번에 다 렌더링하고
   있었던 것**. 홈(찜한 것만)·알림(D-5/3/1만)은 원래 적은 개수만 다루니 안 느렸던 것.
   `FlatList`(화면에 보이는 것만 그리는 가상화 리스트)로 교체해서 해결.
7. **정책 상세 화면 링크를 누르면 "Unable to open URL" 크래시(2026-08-23, 실제 기기 로그로 발견)**
   — 온통청년 원문 URL 필드 중 9건이 `https://` 없이 그냥 도메인만(`www.btp.or.kr` 등) 들어있었음.
   그대로 `Linking.openURL()`에 넘기면 절대경로 URL이 아니라 상대경로로 오인해서
   `file:///.../Expo Go.app/www.btp.or.kr` 같은 알 수 없는 에러가 남. 그중 1건은 아예 URL이 아니라
   "전화문의"라는 안내 문구가 들어있기도 했음. `scripts/syncYouthPolicies.js`에 `normalizeUrl()`을
   추가해서 도메인처럼 생긴 값엔 `https://`를 자동으로 붙이고, URL이 아닌 값은 아예 버림(잘못된
   링크를 보여주는 것보단 나음). 덤으로 `app/deadline/[id].tsx`의 링크 클릭 핸들러도 try/catch로
   감싸서, 앞으로 어떤 이유로든(다른 원인으로 죽은 링크 등) 못 열리면 빨간 에러 화면 대신
   "링크를 열 수 없어요" 알림만 뜨게 함.
8. **검색어를 소문자로 입력하면 대문자 영단어를 못 찾음(2026-08-23)** — `app/search.tsx`가
   `String.includes()`로 제목/카테고리/메타를 검사했는데, 이 메서드는 대소문자를 그대로
   비교함. 그래서 "it"으로 검색해도 제목의 "IT"는 안 걸림. 검색어와 대상 텍스트 양쪽 다
   `.toLowerCase()`로 통일해서 비교하게 고침.
9. **"2026년 평택 청년-기업 이어드림 사업"이 3/2~10/31로 뜨는데 실제 접수는 8/19~8/27이라는
   제보(2026-08-23)** — 우리 코드 버그가 아님을 확인함(온통청년 API에 직접 재조회해봐도
   `aplyYmd`가 지금도 그대로 `"20260302 ~ 20261031"`로 내려옴, 파싱 오류 아님). 원문
   `plcySprtCn`을 보면 이 정책은 **사업기간(2026.1~12월) 동안 "취업멘토링콘서트"/
   "온라인소규모멘토링"/"청년·기업 만남의 장" 같은 개별 모집 회차가 여러 번 도는 연중 프로그램**
   이고, 온통청년은 이런 연중 프로그램에 대해 회차별 접수 기간이 아니라 **사업 전체 기간을
   `aplyYmd`/`bizPrdBgngYmd~EndYmd`에 그대로 넣어둠**. 실제로 웹 검색해보니 8월에 별도로
   "온라인 현직자 특강" 참가자를 모집 중이었음(모집 ~8/21, 선정발표 8/24, 특강 8/27 — 사용자가
   말한 8/19~8/27과 대략 일치). 이 특정 회차 공고는 온통청년 API 레코드에 전혀 반영 안 돼있고
   (`lastMdfcnDt`가 3/27에 멈춰있음), 평택시 게시판 글도 회차마다 새 글이 올라와서 정책 하나에
   묶이지 않음 — 즉 [[youthcenter-api-key-renewal]]에 이미 적어둔 "온통청년 원본 데이터 자체가
   최신이 아닐 수 있고 우리가 감지할 방법이 없다"는 한계와 같은 종류의 문제(안성시 청년내일캠프
   사례와 동일 카테고리)이되, 이번엔 "날짜가 틀림"이 아니라 "연중 다회차 프로그램은 온통청년이
   애초에 회차별 접수 기간을 안 담고 사업 전체 기간만 담는다"는 더 구체적인 원인이 확인됨.
   코드로 고칠 수 있는 부분이 없어 그대로 둠(사용자에게 설명 완료).
   - **후속 조치(같은 날)**: 사용자가 "구청 사이트를 일일이 들어가볼 수도 없는데 이거 해결
     못하나"라고 재질문해서, 이 평택 건이 얼마나 흔한 패턴인지 전수 조사함 — **저장된 508건 중
     470건(92%)이 60일 넘는 신청기간을 가지고 있었고**, 상당수는 온통청년 API가 애초에
     `aplyYmd`란에 사업 전체 운영 기간(몇 년, 심하면 2020~2029처럼 10년)을 그대로 넣어둔
     것이었음(파싱 버그 아님, 원본 데이터 그대로). 회차별 정확한 접수 기간은 알 방법이 없지만
     "이 기간을 못 믿는다"는 것 자체는 코드로 감지 가능해서, `lib/deadlineUtils.ts`의
     `computeDday()`에 새 phase `'longterm'`을 추가함 — 시작일~마감일 span이
     `LONG_TERM_SPAN_DAYS`(90일)를 넘으면 D-day 카운트다운(거짓 정밀도) 대신 "연중 접수"
     배지 + "연중 여러 차례 접수 · 정확한 일정은 공식 링크에서 확인하세요" 안내문으로 대체함
     (카드/상세화면 둘 다). 스타일은 기존 `rolling`(상시모집)과 동일한 주황 계열 재사용 —
     둘 다 사용자 입장에선 "정확한 단일 마감일을 못 믿는다"는 같은 의미. 홈 화면 "진행 중"
     섹션에도 rolling과 같이 포함시킴(신청 자체는 지금도 가능한 상태이므로). DB 스키마 변경
     없이 클라이언트 계산만으로 구현(재동기화 불필요, 새 SQL 실행도 불필요). 재계산 결과:
     active 20 / longterm 467 / closed 11 / before 10 / rolling 9.
